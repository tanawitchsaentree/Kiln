# Accessibility

The floor is in `intensity.md` and applies at every vector. This file is what the system publishes
and how it is verified.

## Target and statement

Name the standard and the level. WCAG 2.2 AA is the common commitment and it is what most
procurement and most regulation expects.

Publish a statement naming what was tested, how, what does not conform, and who to contact. A
blanket claim of compliance gets disproved by the first real user and takes the rest of the
statement with it. Known gaps stated openly are worth more than a claim.

## Keyboard

Every interactive element reachable by keyboard, in an order that matches the visual order.

Publish the keyboard map per component. Arrow keys within a composite, Tab between composites,
Escape to dismiss, Enter and Space to activate. Deviating from these costs the user everything they
learned elsewhere.

Focus never disappears. When a dialog opens, focus moves into it and is trapped. When it closes,
focus returns to what opened it. Both directions, and the return is the one systems forget.

Skip links before any long repeated navigation.

## Focus visible

Always visible, never removed, never animated. Minimum 3:1 against both the element and the
background behind it, which usually means a two-tone ring.

The ring must be visible on every surface the component can sit on, including the darkest and the
most saturated. Test it there rather than on white.

## Colour and contrast

Body text 4.5:1, large text and UI boundaries 3:1, verified against the actual surface in every mode.

Colour never carries meaning alone. Pair it with shape, position, icon, or text. This is a system
rule rather than a component rule, because it is broken at the system level when a status colour is
defined without a status shape.

Test in forced-colours mode. High-intensity systems break there most often and most invisibly, since
the browser overrides exactly the values the identity depends on.

## Motion and preference

Honour `prefers-reduced-motion`, `prefers-contrast`, and `prefers-reduced-transparency`. Three
preferences, three tests.

## Semantics

Native elements before ARIA, always. A styled `button` is better than a `div` with a role, and
almost every accessibility bug in a component library is a div wearing a costume.

Where ARIA is unavoidable, follow the authoring practices pattern for that widget rather than
inventing. Publish which pattern each component implements.

Live regions for anything that changes without user action. Polite by default, assertive only for
errors and only where the user must stop.

## Content

Reading level around ages 12 to 14 for interface copy. Plain language is an accessibility feature
before it is a style preference.

Error text names what went wrong and what to do, and it is associated with the field
programmatically rather than only visually.

## Verification

Automated checks catch roughly a third of issues. Run them in CI on every component and treat a
failure as a build failure.

The other two thirds need a keyboard pass and a screen reader pass per component, recorded in the
component's own documentation. Publish what was tested with, since results differ by combination.

Include real users where the organisation can. Nothing in this file substitutes for that.
